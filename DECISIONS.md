# Décisions

Choix pris sans te demander (option la plus simple), avec leur raison. Les plus récents en bas.

## M0

1. **Versions** : Node 22 dans les images (`node:22-alpine`), pnpm 11.13, Next.js 16.4, React 19.3, Tailwind 4, Drizzle 0.45, Zod 4, ESLint 10, Vitest 5. **TypeScript 6.0** et non 7 : typescript-eslint ne supporte pas encore TS ≥ 6.1.
2. **Packages internes sans étape de build** : `@jobradar/core` et `@jobradar/db` exportent leur source TS. Next les transpile (`transpilePackages`), tsup les bundle pour le worker et migrate, Vitest les lit directement. `moduleResolution: Bundler` partout, donc pas d'extension `.js` dans les imports.
3. **Worker et migrate bundlés en un seul fichier** (tsup, `noExternal` sur tout) : l'image runtime ne contient que `dist/`, sans `node_modules`.
4. **Recherche plein texte** : `jobs.tsv` est une colonne générée `STORED` avec la config `simple` (pas `english`/`french`), parce que les offres mélangent FR et EN et que le stemming d'une langue dégrade l'autre. Poids : titre/entreprise A, lieu B, description C.
5. **Schéma complet dès M0** (toutes les tables de la section 7, plus `kv`) pour éviter une série de migrations. Ajouts par rapport à la spec : `companies.name_key`, `companies.consecutive_failures` (bascule `broken` à 3), `jobs.company_name`, `jobs.canonical_url`, `jobs.missed_runs` (fermeture après 2 runs), `alerts_sent.dedup_key` (unique par canal+type) et la table `kv` (heartbeat du worker, hash de `profile.yaml`, cache LLM).
6. **Session** : JWT HS256 signé avec `AUTH_SECRET` (lib `jose`) dans un cookie httpOnly `jr_session`, `SameSite=Lax`, valable 30 jours, `Secure` si `PUBLIC_BASE_URL` est en https. Le mot de passe est comparé en temps constant (hash SHA-256 puis `timingSafeEqual`), avec un délai de 750 ms après un échec. Pas de verrouillage : l'app est mono-utilisateur.
7. **Protection des routes** : `src/proxy.ts`, la convention Next 16 qui remplace `middleware.ts`. Tout est protégé sauf `/login`, `/healthz` et les assets.
8. **Identifiants Postgres dans compose** : passés par `PGUSER`/`PGPASSWORD` (lus nativement par postgres-js), avec `DATABASE_URL=postgres://db:5432/<db>` sans identifiants. Le mot de passe n'a donc jamais besoin d'être encodé pour une URL (le tien contient des caractères `+/=`).
9. **Ports** : `docker-compose.yml` (prod/Dokploy) ne publie aucun port (`expose` seulement). `docker-compose.override.yml`, chargé automatiquement en local, publie web, worker et db sur `127.0.0.1`. Dokploy lance `docker compose -f docker-compose.yml`, donc l'override n'y est pas appliqué. À confirmer en M6.
10. **CI locale** : `pnpm check` (= `pnpm lint && pnpm typecheck && pnpm test`), parce que `pnpm lint typecheck test` n'enchaîne pas plusieurs scripts.
11. **shadcn/ui** : composants copiés à la main (style new-york, base zinc) au lieu du CLI interactif. `components.json` est présent, donc `pnpm dlx shadcn add <x>` fonctionne pour la suite.
12. **Polices système**, pas de `next/font/google`, pour que le build Docker ne dépende pas du réseau Google.
13. **Branches git** : `main` est la branche principale. Le travail se fait sur des branches `feat/<jalon>-<sujet>` (ex. `feat/m0-scaffold`, `feat/m1-ats-core`), `fix/…`, `chore/…`, `docs/…`, fusionnées par PR. Commits au format conventionnel.

## M1

1. **Dédup** : on cherche d'abord par `(source, source_job_id)` (déjà vu sur cette source), puis par URL canonique, puis par `fingerprint` = sha256(entreprise, titre, ville normalisés), tronqué à 32 caractères. Deux postes identiques (même titre, même ville, même entreprise) avec des req IDs différents deviennent **une** ligne `jobs` avec plusieurs `job_sources` : pour toi, c'est la même offre.
2. **URL canonique** : https, sans `www`, sans hash, sans paramètres de tracking (`utm_*`, `gh_src`, `fbclid`, …), slash final retiré. `gh_jid` est **conservé** parce que c'est l'identifiant du poste sur les pages carrières Greenhouse maison (bug trouvé par les tests sur la fixture Stripe).
3. **Fermeture** : seulement pour les ATS, après 2 runs **complets et réussis** où l'offre est absente (`jobs.missed_runs`). Un run en erreur ne ferme rien. Une offre qui réapparaît est rouverte.
4. **304 Not Modified** : signifie « rien n'a changé », donc toutes les offres ouvertes de ce board sont marquées vues. Les ETag/Last-Modified reçus pendant un run ne sont persistés (table `kv`, clé `etag:<source>:<board>`) **qu'en fin de run réussi**. Sinon, un run planté masquerait des offres derrière un 304 au run suivant.
5. **Requêtes de détail** (SmartRecruiters, Workday) : faites seulement pour les offres pas encore connues **et** dont le titre n'est pas clairement senior/staff/manager/stage (`classify/rules.ts`). Ça divise le volume d'appels (Salesforce : 1 614 offres) sans perdre de candidats new grad. Les autres offres sont stockées à partir des seules données de liste.
6. **`broken`** : 3 échecs consécutifs pour une entreprise, puis `companies.ats_status = 'broken'` et un log `alert: "health"` (l'envoi réel de l'alerte arrive en M5). Un run réussi remet le statut à `ok`.
7. **Client HTTP** : undici, gzip/brotli, pas de suivi de redirection, 2 requêtes simultanées max par hôte, pacing de 1 req/s sur `*.myworkdayjobs.com`, retry exponentiel avec jitter (« equal jitter ») sur 429/5xx/réseau (4 essais), `Retry-After` respecté (au-delà de 2 min, on abandonne).
8. **Planification ATS** : `ATS_CRON` (toutes les 6 h). Les connecteurs tournent en parallèle, chacun démarre après un jitter aléatoire de 0 à 10 min, et les entreprises d'un même connecteur passent séquentiellement, sous un advisory lock Postgres `source:<id>`.
9. **Tests de pipeline** : PGlite (Postgres compilé en WASM, in-process) avec les vraies migrations. Pas de réseau, pas de conteneur. Le code partagé n'utilise que le query builder Drizzle (type `AnyDb`).
10. **Seed** : `syncCompanySeed` est idempotent (au démarrage du worker et avant chaque `cli run`). Il insère les entreprises manquantes et met à jour l'ATS et la priorité depuis le YAML, sans jamais rien supprimer. « Ubisoft Montréal » devient « Ubisoft » parce que le board couvre tous les studios ; Montréal sera favorisée par le score de lieu (M3).

## M2

1. **Lib XML/RSS : `fast-xml-parser` 5.11.2** (version exacte, publiée il y a plus de deux semaines ; la 5.12 avait moins de 15 jours). Zéro dépendance native, gère CDATA, entités HTML et espaces de noms (`tt:location`), bundlée par tsup. Tous les champs restent des chaînes (`parseTagValue: false`) pour ne pas transformer des identifiants en nombres.
2. **Connecteurs paramétrés par `FetchCtx`** : `env` (clés, pays) et `profile` (domaines, lieux) sont passés dans le contexte plutôt que des connecteurs construits à l'exécution. Le registre reste une liste statique et les tests injectent un env factice.
3. **Requêtes des agrégateurs** générées depuis `profile.yaml` : les mots-clés regex (`full[- ]?stack`, `c\+\+`) sont convertis en termes simples (`full-stack`, `c++`). Adzuna : `title_only=<séniorité>` × `what_or=<mots du domaine>` par pays ; Jooble : « new grad software engineer » + « junior <domaine> » × (Canada, United States, Remote) ; JSearch : « new grad software engineer in <lieu> » par lieu le plus pondéré ; Findwork : un mot de séniorité par appel.
4. **Quota** : chaque appel d'une source à clé passe par `ctx.quota.take()` (atomique, `dbQuota`) **avant** la requête ; un refus arrête la source et logge une alerte santé. Testé : jamais plus de N appels, y compris sur deux runs le même jour et deux runs concurrents.
5. **Les agrégateurs ne ferment ni ne rouvrent** : seules les sources ATS (`needsCompany`) remettent `closed_at` à null et `missed_runs` à 0. Une offre fermée par son ATS mais encore listée par SimplifyJobs reste fermée.
6. **Description la plus riche gagnée** : quand une offre est revue (même source, URL canonique ou empreinte), on garde la description la plus longue. Sinon l'extrait Adzuna vu en premier masquait la description complète de l'ATS.
7. **Découverte pendant chaque run** : toutes les URLs d'une offre passent par `detectAts`. Board inconnu → entreprise `discovered` (nom = celui de l'offre) ; entreprise connue sans ATS (même `name_key`) → reçoit le board. Les offres des agrégateurs sont rattachées à l'entreprise du board détecté, sinon à une entreprise de même nom.
8. **Budget de temps du balayage ATS** (`ATS_SWEEP_MAX_MINUTES`, 330 min) : la découverte a ajouté ~960 boards dont ~300 Workday (1 req/s). Les entreprises passent par priorité, puis jamais/le moins récemment OK d'abord, `broken` en dernier ; celles non atteintes avant l'échéance passent en tête au balayage suivant. Pas de chevauchement grâce à l'advisory lock.
9. **Secrets jamais dans les logs ni dans `source_runs.error`** : Adzuna (query string) et Jooble (chemin) mettent leur clé dans l'URL. Le client HTTP masque les valeurs des clés (`***`) dans les URLs loggées et les messages d'erreur, qui s'affichent dans `/sources`.
10. **GitHub** : les listes sont lues sur `raw.githubusercontent.com`, qui n'a pas besoin de token. `GITHUB_TOKEN` ne sert qu'à la recherche de repos (vérification manuelle) et n'est jamais envoyé par le worker.
11. **Amazon** : connecteur ATS dédié, `ats_key` = pays ISO3 récupérés **en entier** (`CAN,FRA`). Les USA (dizaines de milliers d'offres) ne sont pas balayés : couverts par les agrégateurs et SimplifyJobs. Si le plafond de pages est atteint, le run échoue plutôt que de fermer des offres à tort (même règle pour Oracle).
12. **`detect-ats`** : détection par URL d'abord, sinon sondage des API publiques vérifiées avec des slugs tirés du domaine (`careers.stripe.com` → `stripe`). Une seule réponse avec des offres : ajout automatique ; plusieurs : liste affichée, on relance avec l'URL du bon board. Le formulaire de `/companies` ne fait que la détection par URL (aucun appel réseau depuis le dashboard).
13. **HN « Who is hiring? »** : seuls les commentaires de premier niveau au format « Entreprise | Poste | Lieu | … » deviennent des offres (215/242 en novembre 2026) ; titre = premier segment qui ressemble à un poste. Une annonce multi-postes reste une seule offre (le classement fin arrive en M3).
14. **Jooble** : l'`id` est un entier 64 bits que `JSON.parse` arrondit (deux offres pourraient partager le même id). L'identifiant est lu dans le lien `/desc/{id}`, et l'URL stockée est réduite à `https://jooble.org/desc/{id}` (les paramètres de suivi changent à chaque requête).

## M3

1. **Classification par règles d'abord, LLM optionnel.** Ordre : stage/co-op/alternance (titre, type de contrat, indice de source) → titre senior/manager/niveau II+ → marqueur positif du titre (new grad, junior, entry-level, early career, graduate…, et les échelles « Engineer I/1 » comme marqueur faible) → indice de la source → années d'expérience dans la description (> 2 ans = pas new grad, ≤ 1 an = new grad). Un titre qui porte les deux signaux (« Junior/Senior », « Graduate … Director ») reste ambigu (`null`). « Product/Program/Project Manager » nomment un métier, pas un niveau ; « Member of Technical Staff » n'est pas un niveau Staff. Les regex finissent par un lookahead plutôt que `\b`, qui ne marche pas après une lettre accentuée (« diplômé », « expérimenté »).
2. **Jeu de 50 titres réels** (`packages/core/test/fixtures/newgrad-titles.json`), annotés à la main d'après le titre seul : 44 non ambigus, 43 bien classés (97,7 %), précision 23/23 sur ceux étiquetés new grad. Le raté est gardé tel quel (« Senior Engineer … | 0–2 Years of Experience »).
3. **Indices de source : `RawJob.seniorityHint`** (`intern | entry | experienced | executive`), stocké dans `jobs.seniority_hint` (le premier non nul est conservé). Les listes GitHub new grad et Himalayas (filtré « Entry-level ») envoient `entry`, Personio traduit son champ `<seniority>`. Aucun cas particulier par source dans le classifieur.
4. **Score 0-100** (`packages/core/src/score/score.ts`) : lieu = poids du premier critère de `profile.yaml` qui matche (regex sur ville/région/lieu brut, accents ignorés), new grad +25 / inconnu +10 / non 0, domaines 3 points par occurrence (titre ×2, description ×1, plafond 25), langue du profil +5 ou −10 pour une langue hors profil, priorité `high` +10, vue il y a < 24 h +5, salaire affiché +3. Titre ou entreprise exclus = 0 ; pas new grad = plafonné à 20. `score_breakdown` garde chaque ligne (points + détail lisible), le raisonnement new grad et les mots-clés trouvés par domaine.
5. **Filtre par domaine : colonne `jobs.domains text[]` + index GIN** (pas un filtre sur le JSON du breakdown). Un domaine est retenu s'il matche dans le titre ou par au moins 2 mots-clés dans la description : un « node » isolé dans une longue description ne suffit pas.
6. **Recalcul ensembliste** : lots de 1 000 offres en pagination par id, un `SELECT` et un `UPDATE … FROM jsonb_to_recordset($1)` par lot (équivalent d'un `FROM (VALUES …)` avec un seul paramètre, donc pas de limite de 65 535 paramètres). Les lignes inchangées ne sont pas réécrites (`IS DISTINCT FROM`). Mesuré sur la base locale (93 277 offres) : **73 s** la première fois (toutes les lignes écrites), **19 s** quand rien ne change.
7. **Quand recalculer** : `runSource` recalcule les offres touchées par le run (même en échec partiel). Recalcul complet si `sha256(version du scoring + profile.yaml)` diffère de `kv.profile_hash`, vérifié au démarrage du worker et avant chaque balayage (sous l'advisory lock `rescore:full`). Inclure `SCORE_VERSION` dans le hash fait qu'un déploiement qui change les règles recalcule tout, comme une édition du profil. Le hash n'est écrit qu'après un recalcul réussi. Le bonus de fraîcheur est retiré après chaque balayage pour les offres vues il y a plus de 24 h. CLI : `rescore` (forcé) ou `rescore --if-changed`.
8. **LLM optionnel** (`LLM_ENABLED=false` par défaut ; tout marche sans clé) : `@anthropic-ai/sdk` 1.3.0 (version exacte), `claude-haiku-5-5`, `messages.parse` + `zodOutputFormat` (JSON strict `{is_new_grad, seniority, years_required, visa_or_work_auth_notes, language_required}`), effort `low`. Seulement pour les offres que les règles laissent ambiguës, les plus prometteuses (pré-score) d'abord. Plafond `LLM_DAILY_MAX_CALLS` via `dbQuota("llm")`, cache `kv` par empreinte (`llm:<fingerprint>`). Un recalcul complet n'appelle jamais le modèle (cache seulement). Erreur d'auth, 429 ou 5xx : arrêt de la passe. Le score reste une formule : le LLM ne fait que trancher les cas ambigus.
9. **Priorité éditable** : `companies.priority_manual` empêche la synchro du seed d'écraser une priorité modifiée dans le dashboard.

## M4

1. **TanStack Table 8.21.3** (version exacte), pas la 9.x : la v9 change l'API (features, store) et la v8 suffit pour une table à pagination et tri serveur (`manualPagination`, `manualSorting`).
2. **Filtres de l'Inbox dans l'URL** (`apps/web/src/lib/filters.ts`) : seules les valeurs différentes du défaut y figurent (`/?country=CA&ng=yes&min=50&since=24h`). Le serveur valide chaque paramètre (liste blanche, bornes) et construit la requête avec des paramètres liés uniquement. Vue par défaut : offres ouvertes, toutes sauf les ignorées, tri par score.
3. **« Vu depuis »** : fenêtres glissantes (24 h, 72 h, 168 h) sur `first_seen_at`, pas des jours calendaires. Les jours calendaires de Toronto servent pour `/stats` et l'affichage des dates.
4. **Index** vérifiés par `EXPLAIN ANALYZE` sur la base locale (93 277 offres) : vue par défaut 4 ms (`jobs_score_idx`), « Canada + new grad + 24 h + score ≥ 50 » 17 ms (bitmap score × pays), plein texte 42 ms (GIN `tsv`), domaine 6 ms (GIN `domains`), comptage 45 ms. Ajouts : GIN sur `domains` et deux index partiels sur les offres ouvertes (`score desc, first_seen_at desc` et `first_seen_at desc`), utiles quand les offres fermées s'accumuleront.
5. **Description sans `dangerouslySetInnerHTML`** : le HTML est analysé avec `htmlparser2` 12.0.0 (version exacte) et rendu en éléments React à partir d'une liste blanche de balises. Seul attribut gardé : `href` en http(s)/mailto, avec `rel="noopener noreferrer nofollow ugc"`. Scripts, styles, iframes, images et formulaires sont supprimés ; les balises inconnues sont déballées. React échappe tout le texte. Moins de dépendances que `sanitize-html` (pas de postcss).
6. **« Lancer maintenant » sans connecteur dans le web** : le bouton écrit `run_request:<source>` dans `kv`. Le worker réclame ces demandes à son tick d'une minute (`DELETE … RETURNING`, atomique) et lance le run sans bloquer le tick ; l'advisory lock empêche toujours deux runs simultanés d'une même source (une demande qui tombe pendant un run de la même source est ignorée, avec un log). Même mécanisme pour `rescore_request:company:<id>` après un changement de priorité. Pas de nouvelle table.
7. **Le web lit `config/`** (copié dans l'image, `CONFIG_DIR`) : `profile.yaml` pour la liste des domaines et `/settings`, `sources.yaml` pour les quotas de `/sources`. `/settings` compare le hash du fichier à celui appliqué par le worker (`kv.profile_hash`). Le web importe `@jobradar/core/config` et `@jobradar/core/score`, des points d'entrée légers sans le registre des connecteurs ni le SDK LLM.
8. **Raccourcis** : `j/k` naviguer, `s` sauvegarder, `a` postulé, `x` ignorer (même touche une seconde fois = annuler), `o` ouvrir le lien de candidature, `Entrée` ouvrir la fiche. Ignorés quand le focus est dans un champ. Les statuts changent en optimiste puis sont enregistrés par une server action ; en cas d'échec, l'ancien statut revient.
9. **`/pipeline`** : glisser-déposer HTML5 natif entre colonnes, plus un menu de statut sur chaque carte pour le mobile. Pas de bibliothèque de drag & drop.
10. **`/stats`** : barres CSS d'une seule teinte (`--chart-1`), une série par graphique, infobulle native par barre et tableau des valeurs. Pas de bibliothèque de graphiques.
11. **SQL brut** : `queryRows()` (`@jobradar/db`) renvoie les lignes pour postgres-js comme pour PGlite. Avec postgres-js, les `timestamptz` arrivent en chaînes : les fonctions de formatage acceptent `Date | string` (bug trouvé pendant le parcours M4).

## M5

1. **nodemailer 10.3.1** (version exacte, publiée le 2026-10-29, plus de deux semaines ; types inclus, aucune dépendance). ntfy, Discord et Telegram passent par le `fetch` de Node 22 : pas de SDK. Chaque canal n'est actif que si ses variables sont remplies (ntfy : `NTFY_TOPIC` ; e-mail : `SMTP_HOST` + `ALERT_EMAIL_TO` ; Telegram : jeton + chat). Aucun canal = alertes seulement loggées.
2. **Idempotence par réservation** : avant chaque envoi, une ligne `alerts_sent` (canal, type, `dedup_key`) est insérée avec `ON CONFLICT DO NOTHING` ; seul l'appel qui l'insère envoie. Un envoi en échec supprime sa réservation (réessayé au passage suivant, sur ce canal seulement). Un crash entre réservation et envoi perd l'alerte plutôt que de la doubler. Clés : `digest:<heure prévue ISO>`, `job:<id>` (instantanées), `broken:company:<id>:<last_ok_at>`, `broken:source:<source>:<1er run de la série>`, `silence:…`, `no-new:<dernière offre>`, `backup:…` (santé).
3. **Digest ancré sur son heure prévue** (`DIGEST_CRON`, calculée par croner) : fenêtre `[ancre − 24 h, ancre)`, donc deux exécutions pour la même ancre = même contenu et même clé. Le worker le relance toutes les 15 min pendant 12 h (rattrapage après un redémarrage ou une panne SMTP) : rien n'est renvoyé aux canaux qui l'ont déjà. Envoyé même vide (signe de vie quotidien).
4. **Taille du digest** : e-mail limité à 25 offres par pays et 150 au total, avec le lien vers l'Inbox filtrée (`/?since=24h&min=<seuil>`) pour le reste ; la base locale avait 8 457 offres correspondantes après la grosse découverte. Push : compteur + top 5 avec liens. Pays triés par meilleur score. Offres fermées et ignorées exclues.
5. **Alerte instantanée** : offres vues depuis moins de 24 h, new grad ou inconnu, score ≥ `INSTANT_MIN_SCORE`, ou entreprise `priority = high` avec score ≥ `DIGEST_MIN_SCORE` (sinon une offre senior ou exclue d'une entreprise prioritaire sonnerait). Déclenchée après chaque run qui a trouvé des offres (un balayage ATS dure des heures), les appels rapprochés sont fusionnés, et un message groupé quand il y en a plusieurs. Rejouée toutes les 15 min pour les envois en échec.
6. **Santé** (toutes les 15 min et au démarrage) : entreprise `broken` ou source sans entreprise en échec 3 fois de suite (échec dans les 48 h), worker silencieux (heartbeat du process précédent lu au démarrage, ou aucun run terminé depuis `HEALTH_SILENCE_HOURS` alors qu'il tourne), zéro nouvelle offre en 48 h, backup en échec ou de plus de 30 h. Un message groupé par passage, chaque problème une seule fois tant qu'il dure. **Quota épuisé : une ligne dans le digest, pas une alerte instantanée**, parce qu'Adzuna et JSearch épuisent leur quota chaque jour par construction (200/200 et 3/3 en local) : un push quotidien serait du bruit. Un worker complètement arrêté ne peut rien envoyer lui-même : c'est l'alerte « silencieux » au redémarrage, plus le healthcheck Docker et un éventuel moniteur externe sur `/healthz`.
7. **Bouton « Tester les canaux »** : même mécanisme que « lancer » (M4.6). Le web écrit `kv.alert_test_request`, le worker le réclame à son tick (`DELETE … RETURNING`), envoie un aperçu du digest marqué [TEST] sur chaque canal et écrit `kv.alert_test_result`, affiché dans `/settings` (rafraîchie toutes les 10 s tant que la demande est en attente). Rien n'est écrit dans `alerts_sent`. Le web n'importe que `@jobradar/core/alerts/keys` (pas nodemailer).
8. **Variables réduites à un commentaire = vides** : Docker Compose lit `CLE=   # commentaire` comme la valeur « # commentaire ». C'est ce qui faisait répondre ntfy 400/401 : `NTFY_TOPIC` valait « # nom difficile à deviner ». `.env.example` a maintenant tous ses commentaires sur leur propre ligne, et `parseEnv` (comme `/settings`) traite une valeur qui commence par `# ` comme absente.
9. **Tests** : les tests de score et de connecteurs utilisent une copie figée du profil (`packages/core/test/fixtures/profile/`), plus le vrai `config/profile.yaml` : modifier son profil ne casse plus la CI. Vitest limité à 6 processus et 30 s par test : avec un processus par cœur, un processus PGlite plantait sous Windows (0xC0000409).

## M6

1. **Service `backup`** (cible `backup` du Dockerfile, basée sur `postgres:16-alpine` pour avoir le même `pg_dump`) : un dump `--format=custom` compressé par jour à `BACKUP_HOUR` (3 h, Toronto), plus un au démarrage s'il n'y en a pas de moins de 24 h. Écriture dans un fichier `.partial` renommé à la fin, rotation `BACKUP_KEEP_DAYS` (14) jours, volume nommé `backups`. Tourne en `postgres` (uid 70, non-root) ; ne reçoit que les identifiants Postgres, pas tout le `.env`. Healthcheck : un dump de moins de 26 h. Chaque résultat va dans `kv.backup_status`, que la santé du worker surveille (M5.6).
2. **Restauration** : `restore.sh <dump> [base]` vérifie l'archive (`pg_restore --list`), puis `pg_restore --clean --if-exists --no-owner --single-transaction --exit-on-error` (une erreur = rien n'est modifié). Sans base cible : la base de prod (worker et web arrêtés avant). Avec une base cible : créée si besoin, pour tester sans toucher à la prod.
3. **Restauration testée en local** : base de 1,3 Go → dump de 114 Mo en 14 s, restauré dans une base de test en 75 s. Comptes identiques à la prod au moment du dump (93 277 offres, 1 016 entreprises ; les 9 055 offres de plus en prod sont arrivées après le dump, toutes vues après l'heure du dump). La restauration en place n'a pas été jouée sur la base locale (elle aurait effacé les offres arrivées depuis) : même commande, sans base cible.
4. **Revue compose** : limites mémoire db 512m, web 512m, worker 384m, migrate et backup 256m (~1,9 Go au total) ; rotation des logs json-file sur tous les services (10 Mo × 3 à 5) ; images non-root (`node`, `postgres`) ; healthchecks db, worker, web, backup ; `restart: unless-stopped` (migrate : `no`) ; `shm_size: 128m` pour Postgres (64 Mo par défaut, trop peu pour les requêtes parallèles).
5. **Ports (confirme M0.9)** : `docker compose -f docker-compose.yml config` ne publie aucun port, alors que `docker compose config` (override chargé) publie 5432, 3000 et 8081 sur 127.0.0.1. Dokploy déploie avec `-f` et route le domaine vers `web:3000` par son réseau Traefik. Le comportement exact de Dokploy reste à confirmer au premier déploiement (checklist de la PR).

## Multi-utilisateurs (phase 1 : comptes)

1. **Une base d'offres, des scores par personne** : la collecte, la déduplication et la classification de séniorité restent partagées (propres à l'offre). Ce qui dépend de la personne passe dans des tables à clé `user_id` : `job_scores` (score, détail, domaines), `job_status` (statut, notes, relance ; clé `(user_id, job_id)`), `company_prefs` (priorité « haute » = bonus pour cette personne seulement). `companies.priority` ne sert plus qu'à l'ordre de balayage, avec en plus toute entreprise mise en « haute » par quelqu'un.
2. **Reprise sans recalcul** : la migration `0003` crée l'utilisateur 1 (admin) avec le profil appliqué (`kv.profile_hash.text`) et son hash comme `scored_hash`, copie `jobs.score*` dans `job_scores` et rattache statuts et priorités à l'utilisateur 1. Vérifié sur une copie de la base locale (103 166 offres) : nombre, somme et empreinte des 103 109 scores, top 50 de l'Inbox et statuts identiques avant et après ; `cli rescore --if-changed` ne recalcule rien. Les colonnes `jobs.score`, `score_breakdown`, `domains` ne sont plus écrites ; une migration ultérieure les supprimera, une fois la prod vérifiée.
3. **Profils en base** : `users.profile_yaml` (même format que `profile.yaml`). Le worker relit les profils à chaque tick (1 min) et recalcule entièrement les comptes dont `profileHash(profile_yaml)` (texte + `SCORE_VERSION`) diffère de `scored_hash`, tous en un seul passage sur les offres, sous verrou consultatif. Un profil invalide est ignoré (logs et `/settings`), les autres continuent. Nouveau compte : ~37 s pour 103 000 offres. Les offres touchées par un run sont classées une fois puis scorées pour chaque profil (un upsert par lot de 1 000 pour tous les comptes).
4. **Comptes sur invitation** : pas d'inscription publique (quotas d'API et VPS partagés). L'admin crée un lien depuis `/settings` ou `cli user invite <email>` ; seul le hash SHA-256 du jeton est stocké, valable 7 jours, un seul usage (réclamé par `UPDATE … WHERE used_at IS NULL`). Le même mécanisme réinitialise un mot de passe (`user_id` renseigné).
5. **Mots de passe** : scrypt de `node:crypto` (N=16384, r=8, p=1, sel de 16 octets), sans dépendance. Un e-mail inconnu coûte un hachage, comme un mauvais mot de passe. Le propriétaire est amorcé au premier démarrage (worker ou première connexion) depuis `ADMIN_EMAIL` (défaut `CONTACT_EMAIL`) et `DASHBOARD_PASSWORD`, sans jamais écraser une valeur existante.
6. **Session** : le JWT porte l'id de l'utilisateur (`sub`). Le proxy ne vérifie que la signature ; chaque page, action et route charge l'utilisateur (`lib/auth.ts`, `currentUser()`), ce qui coupe l'accès d'un compte supprimé. Les jetons mono-utilisateur (`sub = "owner"`) sont refusés : une reconnexion après le déploiement.
7. **Rôles** : `admin` (comptes, « lancer » une source, canaux d'alerte globaux, réglages techniques) et `user`. Les alertes (canaux du `.env`) partent avec les scores et statuts du propriétaire jusqu'aux alertes par utilisateur (phase 3). Les requêtes des agrégateurs suivent encore le profil du propriétaire (phase 4).
8. **Lint** : `.claude/` et `.impeccable/` (skills et état d'outils, pas du code du projet) sont exclus d'ESLint et de Prettier ; `pnpm check` échouait dessus depuis leur installation.

## Multi-utilisateurs (phase 2 : profil éditable)

1. **Éditeur YAML dans `/settings`** : chaque compte édite son propre profil (même format que `config/profile.yaml`). À l'enregistrement, le serveur vérifie le YAML, le schéma et chaque motif (`profileProblems` : un motif invalide est refusé avec son domaine, alors que `compileProfile` l'ignore en silence pour ne jamais bloquer le score des autres). Le worker voit le nouveau hash au tick suivant et recalcule ce compte (~35 s pour 103 000 offres) ; la page se rafraîchit seule tant que le recalcul est en attente.
2. **Modèles de départ** : `config/profile-templates/` (marketing digital, finance et banque), proposés dans l'éditeur. Testés : YAML valide, aucun motif invalide.
3. **`target_seniority`** (défaut `[entry]`) : niveaux visés parmi `entry`, `mid`, `senior`, `manager`. Niveau visé = 25 points, inconnu = 10, autre niveau connu = plafond 20. Le défaut reproduit exactement l'ancien comportement « new grad » (mêmes libellés, mêmes scores) : pas de changement de `SCORE_VERSION`, donc pas de recalcul des profils existants.
4. **`require_domain`** (défaut `false`) : `true` plafonne à 20 une offre sans mot-clé de domaine dans le titre et avec moins de deux dans la description (la règle des tags de domaine de l'Inbox) ; `title` exige un mot-clé dans le titre. Mesuré avec le modèle marketing sur la base locale : sans l'option, le haut du classement était fait de postes de vente (lieu + junior + langue suffisent à ~60, et un seul « CRM » dans une longue description ajoutait des points) ; avec `true`, encore des SDR (« CRM » et « HubSpot » dans la description) ; avec `title`, le top 25 est entièrement marketing et communication. Les modèles utilisent `title`.
